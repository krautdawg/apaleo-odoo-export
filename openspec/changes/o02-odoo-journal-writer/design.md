## Context

`openspec/research/o-target.md` §1-3 and §6 record how Odoo 17, 18 and 19 import `account.move` records, why only drafts can be imported, why a file cannot create tax lines (`tax_repartition_line_id` is readonly and `base_import` skips readonly fields), and how Odoo computes the VAT of a journal entry in "auto tax mode": the line amount is the base, the tax is rounded per line (17/18 default) or per tax and side (19 default "Round per Tax"), half away from zero, and an unbalanced entry gets an "Automatic Balancing Line" on the suspense account. The engine already has the `TargetWriter<B>` boundary with `currency()` and `movements()` (`src/export/target.ts`). This slice adds the writer only; the posting rules that produce `OdooBooking` values follow in o03.

## Goals / Non-Goals

**Goals:**
- A byte-deterministic CSV that the Odoo import ("Test", then "Import") accepts without column mapping by hand, in 17, 18 and 19.
- Every entry balances to the cent after Odoo's own tax computation, so Odoo never adds a balancing line, and the gross amounts of apaleo stay exact on every non-tax line.
- Every field rule traceable to a source in `docs/odoo-format.md`; every uncertain choice (header names, empty tax cell, External ID form, rounding model) in one constant in `src/odoo/format.ts`, so the first test import changes one line and the golden files.

**Non-Goals:**
- XLSX, partners, invoices, payments, reconciliation, posting, tax tags, tax lines, foreign currency, analytic accounts (research §2: the import needs database ids that no template can know, and a hotel without cost centres gains nothing; `Später geplant` as an optional mapping column).
- The API push (`Später geplant`, research §7).

## Decisions

1. **CSV of `account.move` with one row per line, not journal items.** The model `account.move` carries the entry's External ID and groups its lines without depending on a sequence number (research §1). CSV, not XLSX: no runtime dependency, readable golden files, and Odoo detects separator, quoting and decimal point itself. Format: UTF-8 without BOM, `,` separator, `"` quoting where a value contains `,`, `"`, a line break or starts with a space, LF line ends, `.` as decimal separator with two decimals, dates `YYYY-MM-DD`. Alternative: Odoo 19's misc-operations template layout with labels (`Journal Items/Account`). Rejected: labels are translated in the German UI; technical names (`line_ids/account_id`) match in every language (open question 1).
2. **One entry per property and business day; lines netted per (account, tax, label).** Research §6. The netting key keeps payment methods apart (`Zahlung Visa`, `Zahlung Mastercard` on `1360`) for the bank reconciliation, and gives each base line exactly one side, so it maps to one tax repartition (invoice side for credits, refund side for debits, as Odoo's `_compute_is_refund` decides). A key whose net is 0 produces no line and is counted in the protocol. Alternative: one entry per apaleo line. Rejected: thousands of entries per month and more fitting cents.
3. **Odoo computes the VAT; the file carries the base and the tax External ID.** Never a tax line, never `tax_tag_ids` (research §3, options B-D). The tax column holds the External ID `account.<odoo.companyId>_<template id>` (for example `account.1_tax_ust_19_skr03`); a mapping value that already contains a `.` is written as is (custom taxes). Every line writes the tax column, empty for untaxed lines, because an empty cell sets "no taxes" explicitly and stops Odoo 17/18 from adding the account's default tax (SKR04 `4200` carries 19 %).
4. **Base fitting with a TypeScript model of Odoo's tax.** `odooTax(lines, mode)` returns the tax per (tax, side) exactly as Odoo computes it for entries: `per_line` = sum of `roundHalfAwayFromZero(base × rate / 100)` per base line; `per_tax` = `roundHalfAwayFromZero(rate / 100 × Σ base)` per (tax, side) group of the entry. `fit()` then chooses, for each base line (`per_line`) or group (`per_tax`), the base `B` nearest to apaleo's net with `B + odooTax(B) = G` (apaleo's gross of that line or group), searching ±3 cents. When no `B` exists (the rounding jumps over `G`, about 16 % of values at 19 %): with `per_line` the line gets a companion base line of `0.01` (or `-0.01`) on the same account and tax labelled `<label> (Rundungsausgleich)`, whose tax rounds to `0.00`; with `per_tax` the cent goes on an untaxed line on `odoo.roundingAccount` labelled `Rundungsausgleich USt <rate> %`, because a split inside the group cannot change a per-group rounding. In `per_tax` mode a group spread over several accounts gets its fitted base distributed by apaleo's nets with the largest-remainder method. Every adjustment raises `N-ODOO-ROUNDING-LINE` with day, account and amount. Alternative: carry apaleo's net and let Odoo balance. Rejected: Odoo would book the difference on the suspense account without telling anyone.
5. **The rounding mode is configuration, with a version default.** `odoo.taxRounding` defaults to `per_line` for `odoo.version` 17 and 18 and to `per_tax` for 19 (the Odoo company defaults), and the import block tells the accountant to compare it with Settings > Accounting > Taxes > "Rounding Method" (an upgraded database keeps its old setting). `odoo.roundingAccount` is required with `per_tax` (config error otherwise) and must not carry a default tax.
6. **Validation proves the file before it is written.** `E-ODOO-UNBALANCED` when an entry's debits minus credits plus the modelled Odoo tax are not 0; `E-ODOO-GROSS` when a (tax, side) group's base plus tax differs from the bookings' gross; `E-ODOO-VAT-FIT` when Odoo's tax of a group differs from apaleo's rounded tax by more than one cent per apaleo line plus one (a defect guard: the fitting can move the tax only by that much); `E-ODOO-ACCOUNT` (code not `^[A-Za-z0-9.]{1,64}$`, Odoo's own rule), `E-ODOO-TAX-REF` (not `^[a-z0-9_]+$` or `^[A-Za-z0-9_]+\.[A-Za-z0-9_]+$`), `E-ODOO-JOURNAL` (not 1 to 5 characters `A-Z0-9`, Odoo's size limit), `E-ODOO-SAME-ACCOUNT`, `E-ODOO-AMOUNT` (gross not positive whole cents), `E-ODOO-DATE` (outside the period), `E-ODOO-TAX-ON-ROUNDING` (rounding account equals a taxed base account). All findings at once in one `OdooValidationError` (a `FindingsError`).
7. **External IDs: `apaleo_c<companyId>_<propertyId>_<YYYYMMDD>` and `..._<NNNN>` for lines, `_r<N>` for a replacement.** No module prefix (Odoo adds `__import__`), so the IDs are unique per database and company, and the same file imported twice updates its own drafts instead of duplicating (research §2). A replacement file (revision N ≥ 2, written by `--overwrite`) carries `apaleo_c1_BSP_20260914_r2` and `apaleo_c1_BSP_20260914_r2_0001` and the `ref` suffix ` (Korrektur 2)`, because a reversal does not free the External ID of a posted entry: a corrected file with the old IDs would update the posted move and Odoo would refuse the whole file, and over a draft it would keep the lines the new file no longer has (research §2, §6). With the revision the corrected file always creates new entries after the accountant deleted the drafts or reversed the posted entries of the earlier revision. The writer renders the revision it is given and reads it back from an existing file (`revisionOf()`); choosing it is the pipeline's job (o06). Alternative: delete the External ID of the reversed entry under Settings > Technical > External Identifiers. Rejected: error-prone, needs developer mode, and a forgotten step merges lines silently. The demo uses `apaleo_c1_BSP_DEMO_...`. `ref` is `apaleo <propertyId> <YYYY-MM-DD>` (demo: `DEMO apaleo ...`) so the accountant can filter. `name` (the entry number) stays empty for Odoo's sequence.
8. **Labels without personal data, sanitised.** `line_ids/name` is the label of the netting key (from the posting rules, o03): no guest names, control characters removed, runs of spaces collapsed, at most 128 characters (`N-ODOO-TRUNCATED`). The receipt numbers of the apaleo lines are not on the lines (a netted line has many); the protocol lists them per entry line.
9. **Movement model per booking stays apaleo's.** `movements()` of an `OdooBooking` returns the counter side with the gross and the VAT side with the gross minus apaleo's tax, as for Abacus, so the existing `E-ACCOUNT-BALANCE` check is unchanged. The fitting cents are checked inside the writer (decision 6) and shown in the import block.
10. **Check the model against real Odoo before anything is built on it.** The tax design rests on reading Odoo source (base fitting, the 0.01 companion line, the per-tax rounding-account line, the empty `line_ids/tax_ids/id` cell against account default taxes in 17/18, the technical headers). The last task group of this slice is a maintainer-run import into throwaway local Odoo 17, 18 and 19 containers with SKR03 and SKR04 (`scripts/odoo-check/`, run with `odoo shell` inside the container: no API key, no credentials, no hosted Odoo, not in CI) that imports every golden file through `base_import` and reports tax lines, balancing lines, states, re-import behaviour and the generated cash and transfer account codes. The results go to `## Testimporte` (reviewer "Maintainer, lokal" until a Kanzlei confirms) and answer research §10 questions 1, 2, 4, 5, 6, 8, 9 and 11; constants in `src/odoo/format.ts` and the golden files are adjusted before o03 starts. Alternative: wait for the Steuerberater's test import before the release. Rejected: o03 to o08 would build mapping, demo and docs on an unchecked model, and a difference (for example per-line netting, `is_refund` on a debit base line, or 19.0's `round_globally` grouping key) would mean reworking most golden files, docs and the demo.

## Risks / Trade-offs

- [Odoo's computation differs from the model in some version (for example a hidden rounding of the base in 18)] → the local test import of task group 7 runs every golden file through real Odoo 17, 18 and 19 before o03; the model is one module with unit tests built from Odoo's own docstring examples, and the import block tells the accountant to look for an "Automatic Balancing Line" after the first import.
- [Odoo's VAT differs from apaleo's per-line VAT by a few cents per month] → shown per rate and month in the protocol; the docs ask the Steuerberater to accept it (research open question 3); the API path with explicit tax amounts is the later alternative.
- [Header names not recognised in a translated UI] → technical names are language-independent; open question 1; one constant `CSV_HEADER` in `format.ts`.
- [Account code prefix search in 19 picks `84001` for `8400`, and also matches an account whose description contains `8400`; in a database with several companies every active company is searched] → documented in `docs/odoo-format.md` with the "Test" step that shows "multiple matches", and the import block and `docs/odoo-import.md` (o04) say to activate only the target company in the company switcher; open questions 6 and 11, checked by the local test import.
